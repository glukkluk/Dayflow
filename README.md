# Особистий розклад

Python 3.14+, Django 6.1, **PostgreSQL 16+** (розроблено й перевірено на PostgreSQL 16). Залежності керуються через `uv` (`uv.lock`); зафіксований список у `requirements.txt`.

## Запуск

1. Створіть базу PostgreSQL і користувача:

```sql
CREATE USER dayflow WITH PASSWORD 'your-password' CREATEDB;  -- CREATEDB потрібен для тестів
CREATE DATABASE dayflow OWNER dayflow;
```

2. Скопіюйте `.env.example` у `.env` і заповніть значення (`.env` ігнорується git):

| Змінна | Призначення |
|---|---|
| `SECRET_KEY` | секретний ключ Django (`python -c "from django.core.management.utils import get_random_secret_key as g; print(g())"`) |
| `DEBUG` | `True` для розробки |
| `ALLOWED_HOSTS` | хости через кому (типово `localhost,127.0.0.1`) |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD` | доступ до БД |
| `DB_HOST`, `DB_PORT` | типово `localhost`, `5432` |

3. Встановіть залежності та запустіть:

```sh
# варіант з uv
uv sync
# або через venv + pip
python -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt

python app/manage.py migrate
python app/manage.py seed_demo      # демо-дані: demo_user, demo_manager (пароль demo-pass-2026)
python app/manage.py runserver
```

`seed_demo` ідемпотентна; `--reset` перестворює демо-користувачів, `--password` задає пароль.

## Реалізований етап: облікові записи

- Реєстрація за username, обов'язковим email та підтвердженим паролем.
- Стандартні перевірки й хешування паролів Django, вхід із підтримкою `next`, вихід через POST із CSRF.
- Нові паролі хешуються Argon2id (`argon2-cffi`) зі стандартними параметрами Django. Наявні PBKDF2-паролі залишаються дійсними й автоматично перехешовуються після успішного входу; перший такий вхід ще потребує повільної PBKDF2-перевірки. Міграція БД та скидання паролів не потрібні.
- Автоматичне створення одного профілю через `post_save`; міграція додає профілі наявним користувачам.
- Редагування власного часового поясу, робочого дня й буфера (0–60 хв).
- Типові налаштування: Europe/Kyiv, 09:00–18:00, 10 хв.
- Валідація робочого часу у формі та обмеження в БД; часовий пояс активується на час запиту.
- Україномовні сторінки реєстрації, входу та профілю.

## Реалізований етап: категорії та базові події

- `/categories/`: список, створення, редагування та підтвердження видалення категорій.
- Назви категорій унікальні в межах власника; колір перевіряється як `#RRGGBB`.
- П'ять стандартних категорій створюються для нових користувачів. Наявні користувачі можуть додати категорії вручну.
- `/events/`: список із пошуком за назвою/описом та пагінацією по 20 записів.
- Створення, деталі, редагування й підтвердження видалення події; необов'язкова категорія та прапорець «Весь день».
- Час вводиться й відображається в поясі профілю, зберігається в UTC. Неоднозначний або неіснуючий локальний час відхиляється стандартною валідацією Django.
- Кінець строго пізніше за початок: перевірка форми й обмеження БД.
- Чужі записи за прямим URL повертають 404, вибір чужої категорії відхиляється.
- Видалення категорії скидає посилання подій у `NULL`; видалення виконується лише POST-запитом із CSRF.

Адреси категорій використовують числовий ID, стабільний при перейменуванні.

## Реалізований етап: in-app нагадування (замість email)

- Повідомлення показуються одразу в системі — без email. Доставка: тости в інтерфейсі + окремий розділ «Повідомлення».
- `GET /notifications/` — розділ «Повідомлення»: список із позначенням «Позначити прочитаним» (HTMX) та кнопка «Позначити всі прочитаними» (POST).
- Тости (`toasts.js`): опитує `GET /api/notifications/pending/` кожні 30 с і показує нові нагадування спливаючими повідомленнями **справа знизу** на будь-якій сторінці. Показ тосту не позначає повідомлення прочитаним — лічильник у меню зростає й лишається, поки не відкрити розділ «Повідомлення».
- Розрізнення «був у системі» / «не було в системі»: поле `Notification.delivered_at` фіксує показ тостом. Перший запит сторінки йде з `?silent=true` — він лише оновлює лічильник і споживає накопичене. Тому повідомлення, що настали, поки користувач був вийдений, **не показуються тостами**, а збільшують лише badge.
- `POST /api/notifications/read/` позначає прочитаними за id або всі одразу; лічильник оновлюється наступним опитуванням.
- Нагадування про подію: `Event.reminder_minutes` (5/15/30/60 хв або 1 день, FR-3.7) у формі події; для повторюваних серій повідомлення створюється на кожен екземпляр.
- Нагадування про дедлайн завдання — за 24 години (FR-8.5).
- Дедуплікація: унікальні обмеження БД `(event, occurrence_start)` та `(task, kind)` + транзакційна вставка з ігноруванням конфліктів; повторні опитування не створюють дублікатів.
- Одноразова подія, що вже почалась, не нагадує; екземпляр із неоднозначним DST-часом пропускається без падіння.

## Реалізований етап: завдання

- `/tasks/`: список, створення, редагування та підтвердження видалення на Generic Views.
- Необов'язковий дедлайн у поясі профілю, категорія, три пріоритети та оцінка тривалості 5–480 хв.
- Статуси: «До виконання», «У роботі», «Виконано». Завершення встановлює `completed_at`, повернення в інший статус очищає його.
- Фільтри за статусом, пріоритетом, категорією та простроченням; пошук за назвою/описом.
- Сортування за дедлайном (без дедлайну — в кінці), пріоритетом або датою створення; по 20 завдань на сторінці.
- Кнопка «Виконано» оновлює список через HTMX зі збереженням фільтрів. Для виконаного завдання кнопка повертає статус «До виконання».
- HTMX 2.0.8 завантажується з CDN із перевіркою цілісності. Без JavaScript відмітка працює звичайним POST із перенаправленням.
- Видалення категорії зберігає завдання без категорії. Чужі завдання повертають 404, POST-запити захищені CSRF.

Логіка часу завершення зосереджена в моделі `Task`; обмеження БД перевіряють узгодженість статусу й `completed_at`, діапазон тривалості та пріоритет.
Змінюйте статус через `save()`: `QuerySet.update()` не викликає логіку моделі.

## Реалізований етап: вільні завдання

- Вільне завдання — звичайне завдання без дедлайну з орієнтовною тривалістю 5–480 хв. Наявна форма створення й редагування має прапорець «Без дедлайну — вільне завдання»; він прибирає дедлайн. Окремого типу чи моделі немає.
- На дашборді поле «Вільний час» має вибір одиниць: 1–59 хвилин або 1–24 години (цілі числа). Межі перевіряються браузером і сервером; години перетворюються на хвилини для підбору. «Взяти вільне завдання» відкриває діалог із власними завданнями без дедлайну, зі статусом «До виконання», без подій у календарі та з тривалістю не більшою за введений час. Порядок: високий пріоритет, коротша тривалість, ID.
- У списку завдань поруч із «Лише прострочені» є фільтр «Вільні завдання» — усі завдання без дедлайну, з урахуванням решти фільтрів і пошуку.
- У формі не можна створити вільне завдання зі статусом «У роботі», вручну почати його або прибрати дедлайн у завдання, яке вже в роботі. Редагування вже взятого вільного завдання залишається доступним.
- «Взяти в роботу» через POST із CSRF повторно перевіряє доступність і тривалість, створює подію від поточного часу на орієнтовну тривалість із посиланням `source_task` та змінює статус на «У роботі» однією транзакцією. Перевірка конфліктів враховує повторення за загальними правилами подій. За наявності накладань зміни не зберігаються: спочатку показано попередження з можливістю скасувати або «Взяти й розмістити все одно». Підтвердження повторно перевіряє доступність і конфлікти.
- Біля кнопки підбору є посилання «Усі вільні завдання» на `/tasks/?free=on`. Без JavaScript підбір працює окремою сторінкою `/tasks/free/`.

## Реалізований етап: автопланування

- Кнопка «Розмістити завдання в розклад» на сторінках завдань і календаря веде на `/tasks/autoplan/`.
- Плануються завдання зі статусом «До виконання» без уже прив'язаних подій; порядок: пріоритет (високий → низький), ближчий дедлайн (без дедлайну — останні), коротша тривалість.
- Горизонт: від зараз до дедлайну або 14 днів без дедлайну. Блок завжди закінчується не пізніше дедлайну.
- Слоти шукаються лише в робочих годинах профілю у вільних проміжках між наявними подіями (включно з повторюваними серіями; події «весь день» блокують день цілком). Сьогодні — від `max(now, work_start)`, округленого вгору до 5 хв.
- Між блоками — буфер із профілю. Довге завдання розбивається на блоки від 25 хв; сума блоків дорівнює оцінці.
- Попередній перегляд групує блоки за завданнями й показує блок «Не вдалося розмістити» з причиною. POST перераховує план і створює всі події однією транзакцією (`transaction.atomic` — або всі, або жодна), потім веде до календаря.
- Подія автопланування має назву, опис і категорію завдання та поле `source_task` (видно в календарному API як `extendedProps.source_task`). Повторний запуск не створює дублікатів; у списку завдань такі завдання позначені «Розміщено в розкладі».
- Видалення завдання видаляє й розміщені для нього події (`on_delete=CASCADE`); сторінка підтвердження попереджає про це.
- Зламана серія з неоднозначним часом у горизонті не падає з 500: сторінка показує помилку з проханням виправити подію.

Не реалізовано (пріоритет C): кнопка «Скасувати автопланування» (FR-7.12).

Наступні кроки: FR-1.7 (зміна пароля, S), FR-5.9 (маркери дедлайнів завдань у календарі, S), власні сторінки 404/500 (C), продакшн-налаштування й деплой.

## Реалізований етап: повторення та дані календаря

- У формі події доступні повторення: немає, щодня, щотижня, щомісяця та необов'язкова кінцева дата включно.
- Одна серія — один запис у БД. Редагування й видалення стосуються всієї серії.
- `planner/services/recurrence.py` розгортає лише екземпляри, що перетинають запитаний діапазон `[start, end)`; результати містять UTC-дату початку й кінця.
- Початок і кінець повторень зберігають локальний час у поточному поясі профілю. Зміна поясу профілю змінює пояс розгортання серій.
- Щомісячні дати обчислюються від початкового числа: 31 січня → 28/29 лютого → 31 березня. Реалізація використовує стандартні `calendar` і `zoneinfo`.
- Неіснуючий або неоднозначний локальний час екземпляра відхиляється; API повертає 400 із `code=invalid_occurrence_time` та `event_id`, щоб можна було виправити серію.
- `GET /api/events/?start=2026-10-01T00:00:00Z&end=2026-11-01T00:00:00Z` повертає масив подій у форматі FullCalendar, лише для поточного користувача.
- Межі мають містити часовий пояс, кінець строго пізніше початку, максимальний діапазон — 366 днів. У URL символ `+` у зміщенні слід кодувати як `%2B` (або використовувати `Z`/`URLSearchParams`).
- `id` у відповіді — ID серії; дата `start` визначає конкретний екземпляр. Колір без категорії — сірий `#6B7280`.
- Для «Весь день» повертаються дати, кінець виключний: неповний останній день включається цілком. Для звичайних подій — ISO-час зі зміщенням профілю.

## Реалізований етап: календар і конфлікти

- `/calendar/`: FullCalendar із режимами дня, тижня, місяця та списку, українською локалізацією, кнопкою «Сьогодні» та робочими годинами профілю.
- FullCalendar і Luxon завантажуються з CDN у фіксованих версіях. Luxon забезпечує правильне відображення поясу профілю незалежно від поясу браузера.
- Клік по порожньому слоту відкриває форму з підставленим часом; клік по події — діалог із деталями, редагуванням і переходом до підтвердження видалення.
- Перетягування й розтягування надсилають PATCH із CSRF. Помилка або скасування конфлікту відновлює попереднє положення.
- Переміщення екземпляра повторюваної події зсуває початок усієї серії в локальному часі; її кінцева дата залишається заданою користувачем. Перетягування між годинною сіткою й областю «весь день» вимкнено; прапорець можна змінити у формі.
- `planner/services/conflicts.py`: інтервали `[start, end)`, стикання не є конфліктом, власна подія виключається, чужі події недоступні. Події «весь день» не беруть участі у перевірці конфліктів.
- Для кінцевих серій перевіряються всі екземпляри; для нескінченних — 365 днів від `max(start, now)`. Межа відображається у попередженні. Цей горизонт погоджено з користувачем.
- Конфлікти перевіряються при створенні, редагуванні та переміщенні. «Зберегти все одно» дозволяє лише накладання, але не обходить валідацію даних і часу.
- `PATCH /api/events/<id>/move/`: `start`, `end` — ISO зі зміщенням, `force` — boolean. Для серії обов'язкове `occurrence_start` із `extendedProps` початкового екземпляра. Відповіді: 200 / 409 із `conflicts` та межами перевірки / 400 / 404.
- `POST /api/events/check-conflicts/`: `start`, `end`, необов'язковий власний `exclude_id`; перевірка конкретного інтервалу до 366 днів.

## Реалізований етап: дашборд

- Головна сторінка `/` і пункт меню «Дашборд» доступні після входу. Дані належать лише поточному користувачу.
- «Сьогодні»: усі події, що перетинають локальний день, у хронологічному порядку, включно з повтореннями, багатоденними та автоподіями. Поточні події позначені «Зараз триває».
- «Найближчі дедлайни»: перші 3 незавершені завдання за зростанням дедлайну, який ще не минув. У цьому ж блоці окремо показано загальну кількість прострочених із посиланням на фільтр; у легенді кругової діаграми залишаються лише три статуси завдань.
- «Цей тиждень»: за погодженим правилом усього — завдання з дедлайном цього тижня, виконано — ті з них, що зараз мають статус `done`. Завдання без дедлайну не входять у цей показник. Для порожнього тижня відсоток дорівнює 0.
- Межі дня й тижня (понеділок–неділя) обчислюються у часовому поясі профілю; порівняння та тривалості — у UTC, з урахуванням переходів часу.
- Таблиця часу за категоріями підсумовує тривалості годинних подій лише всередині тижня. Події «весь день» виключені; накладені події додаються окремо. Некатегоризовані події згруповано як «Без категорії».
- Якщо повторення має помилку DST, показано пояснення та посилання на редагування. Решта даних доступна; таблиця явно позначена як потенційно неповна.
- Обчислення винесені в `planner/services/dashboard.py`, сторінка використовує `TemplateView`. Нові моделі та міграції не потрібні.

## Перевірка

### Зручність інтерфейсу

- Завдання: швидкі фільтри, пошук із затримкою 400 мс без перезавантаження, стан завантаження та URL зі збереженими фільтрами. Кнопки браузера «Назад/Вперед» відновлюють пошук; без JavaScript працює звичайна GET-форма.
- Форми: позначення обов'язкових полів, зведення помилок із посиланнями, видимий стан збереження та доступні під час прокручування кнопки дій.
- На телефоні доступне розгортання меню; поля пароля мають кнопку показу, профіль — переходи до розділів.
- Окреме повідомлення можна позначити прочитаним через POST із CSRF, також без JavaScript. Чужі та некоректні ID повертають 404.

```sh
uv run python app/manage.py check
uv run python app/manage.py test accounts planner
```

## Реалізований етап: розширений профіль

- Сторінка `/profile/` складається з незалежних форм (поле `action`): загальні налаштування, зміна імені користувача, аватар, зміна пароля (сесія зберігається) та «Небезпечна зона» — видалення акаунту з підтвердженням паролем і прапорцем; разом з користувачем каскадно видаляються всі його дані та файл аватара.
- Аватар: `Profile.avatar` (Pillow), до 5 МБ, обрізається до квадрата 256×256 і зберігається як WebP у `MEDIA_ROOT/avatars/<user_id>/`; старий файл видаляється при заміні. У режимі `DEBUG` файли віддає Django, у продакшені `MEDIA_ROOT` має віддавати вебсервер.
- Формат дати (`ДД.ММ.РРРР`, `ДД/ММ/РРРР`, `ММ/ДД/РРРР`, `РРРР-ММ-ДД`) і часу (24-/12-годинний) зберігаються в профілі та застосовуються до списків, дашборда, сповіщень і календаря (context processor `display_formats`, `accounts/formats.py`). Поля введення часу у формі події лишаються 24-годинними.
- Часовий пояс вибирається зі списку, згрупованого за регіонами, із поточним зміщенням UTC.
- Біля кожного налаштування є значок «?» з підказкою (опис і приклад), що показується при наведенні або фокусі.

## Ролі й доступ

- Дві ролі: звичайний користувач і **Менеджер** (група `Менеджер`, створюється data-міграцією `planner/0010_create_manager_group`).
- Група має право `planner.view_all_events` (`Event.Meta.permissions`). Воно відкриває сторінку `/manager/events/` — перегляд подій усіх користувачів із пошуком за назвою або автором.
- Менеджер може переглядати деталі чужих подій, але завдання, категорії та повідомлення доступні лише власні. Категорії чужих подій приховані в списку й деталях. Редагувати та видаляти можна лише власні події.
- Право перевіряється на сервері (`PermissionRequiredMixin`): без нього користувач отримує 403, гість — перенаправлення на вхід. Пункт меню «Усі події» лише відображає цей стан.
- Додати користувача до ролі: адмінка → Користувачі → Групи, або `seed_demo` (`demo_manager`).
