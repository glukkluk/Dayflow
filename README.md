# Особистий розклад

Python 3.14+, Django, SQLite. Залежності керуються через `uv` і зафіксовані в `uv.lock`.

## Запуск

```sh
uv sync
uv run python app/manage.py migrate
uv run python app/manage.py runserver
```

## Реалізований етап: облікові записи

- Реєстрація за username, обов'язковим email та підтвердженим паролем.
- Стандартні перевірки й хешування паролів Django, вхід із підтримкою `next`, вихід через POST із CSRF.
- Автоматичне створення одного профілю через `post_save`; міграція додає профілі наявним користувачам.
- Редагування власного часового поясу, робочого дня й буфера (0–60 хв).
- Типові налаштування: Europe/Kyiv, 09:00–18:00, 10 хв.
- Валідація робочого часу у формі та обмеження в БД; часовий пояс активується на час запиту.
- Україномовні сторінки реєстрації, входу та профілю.

## Реалізований етап: категорії та базові події

- `/categories/`: список, створення, редагування та підтвердження видалення категорій.
- Назви категорій унікальні в межах власника; колір перевіряється як `#RRGGBB`.
- П'ять стандартних категорій створюються для нових користувачів. Наявні користувачі можуть додати категорії вручну.
- `/events/`: список із пошуком за назвою/описом та пагінацією по 20 записів.
- Створення, деталі, редагування й підтвердження видалення події; необов'язкова категорія та прапорець «Весь день».
- Час вводиться й відображається в поясі профілю, зберігається в UTC. Неоднозначний або неіснуючий локальний час відхиляється стандартною валідацією Django.
- Кінець строго пізніше за початок: перевірка форми й обмеження БД.
- Чужі записи за прямим URL повертають 404, вибір чужої категорії відхиляється.
- Видалення категорії скидає посилання подій у `NULL`; видалення виконується лише POST-запитом із CSRF.

Адреси категорій використовують числовий ID, стабільний при перейменуванні.
Нагадування та автопланування — наступні етапи.

## Реалізований етап: завдання

- `/tasks/`: список, створення, редагування та підтвердження видалення на Generic Views.
- Необов'язковий дедлайн у поясі профілю, категорія, три пріоритети та оцінка тривалості 5–480 хв.
- Статуси: «До виконання», «У роботі», «Виконано». Завершення встановлює `completed_at`, повернення в інший статус очищає його.
- Фільтри за статусом, пріоритетом, категорією та простроченням; пошук за назвою/описом.
- Сортування за дедлайном (без дедлайну — в кінці), пріоритетом або датою створення; по 20 завдань на сторінці.
- Кнопка «Виконано» оновлює список через HTMX зі збереженням фільтрів. Для виконаного завдання кнопка повертає статус «До виконання».
- HTMX 2.0.8 завантажується з CDN із перевіркою цілісності. Без JavaScript відмітка працює звичайним POST із перенаправленням.
- Видалення категорії зберігає завдання без категорії. Чужі завдання повертають 404, POST-запити захищені CSRF.

Логіка часу завершення зосереджена в моделі `Task`; обмеження БД перевіряють узгодженість статусу й `completed_at`, діапазон тривалості та пріоритет.
Змінюйте статус через `save()`: `QuerySet.update()` не викликає логіку моделі.

## Реалізований етап: автопланування

- Кнопка «Розмістити завдання в розклад» на сторінках завдань і календаря веде на `/tasks/autoplan/`.
- Плануються завдання зі статусом «До виконання» без уже прив'язаних подій; порядок: пріоритет (високий → низький), ближчий дедлайн (без дедлайну — останні), коротша тривалість.
- Горизонт: від зараз до дедлайну або 14 днів без дедлайну. Блок завжди закінчується не пізніше дедлайну.
- Слоти шукаються лише в робочих годинах профілю у вільних проміжках між наявними подіями (включно з повторюваними серіями; події «весь день» блокують день цілком). Сьогодні — від `max(now, work_start)`, округленого вгору до 5 хв.
- Між блоками — буфер із профілю. Довге завдання розбивається на блоки від 25 хв; сума блоків дорівнює оцінці.
- Попередній перегляд групує блоки за завданнями й показує блок «Не вдалося розмістити» з причиною. POST перераховує план і створює всі події однією транзакцією (`transaction.atomic` — або всі, або жодна), потім веде до календаря.
- Подія автопланування має назву, опис і категорію завдання та поле `source_task` (видно в календарному API як `extendedProps.source_task`). Повторний запуск не створює дублікатів; у списку завдань такі завдання позначені «Розміщено в розкладі».
- Видалення завдання видаляє й розміщені для нього події (`on_delete=CASCADE`); сторінка підтвердження попереджає про це.
- Зламана серія з неоднозначним часом у горизонті не падає з 500: сторінка показує помилку з проханням виправити подію.

Не реалізовано (пріоритет C): кнопка «Скасувати автопланування» (FR-7.12).
Нагадування та дашборд — наступні етапи.

## Реалізований етап: повторення та дані календаря

- У формі події доступні повторення: немає, щодня, щотижня, щомісяця та необов'язкова кінцева дата включно.
- Одна серія — один запис у БД. Редагування й видалення стосуються всієї серії.
- `planner/services/recurrence.py` розгортає лише екземпляри, що перетинають запитаний діапазон `[start, end)`; результати містять UTC-дату початку й кінця.
- Початок і кінець повторень зберігають локальний час у поточному поясі профілю. Зміна поясу профілю змінює пояс розгортання серій.
- Щомісячні дати обчислюються від початкового числа: 31 січня → 28/29 лютого → 31 березня. Реалізація використовує стандартні `calendar` і `zoneinfo`.
- Неіснуючий або неоднозначний локальний час екземпляра відхиляється; API повертає 400 із `code=invalid_occurrence_time` та `event_id`, щоб можна було виправити серію.
- `GET /api/events/?start=2026-10-01T00:00:00Z&end=2026-11-01T00:00:00Z` повертає масив подій у форматі FullCalendar, лише для поточного користувача.
- Межі мають містити часовий пояс, кінець строго пізніше початку, максимальний діапазон — 366 днів. У URL символ `+` у зміщенні слід кодувати як `%2B` (або використовувати `Z`/`URLSearchParams`).
- `id` у відповіді — ID серії; дата `start` визначає конкретний екземпляр. Колір без категорії — сірий `#6B7280`.
- Для «Весь день» повертаються дати, кінець виключний: неповний останній день включається цілком. Для звичайних подій — ISO-час зі зміщенням профілю.

## Реалізований етап: календар і конфлікти

- `/calendar/`: FullCalendar із режимами дня, тижня, місяця та списку, українською локалізацією, кнопкою «Сьогодні» та робочими годинами профілю.
- FullCalendar і Luxon завантажуються з CDN у фіксованих версіях. Luxon забезпечує правильне відображення поясу профілю незалежно від поясу браузера.
- Клік по порожньому слоту відкриває форму з підставленим часом; клік по події — діалог із деталями, редагуванням і переходом до підтвердження видалення.
- Перетягування й розтягування надсилають PATCH із CSRF. Помилка або скасування конфлікту відновлює попереднє положення.
- Переміщення екземпляра повторюваної події зсуває початок усієї серії в локальному часі; її кінцева дата залишається заданою користувачем. Перетягування між годинною сіткою й областю «весь день» вимкнено; прапорець можна змінити у формі.
- `planner/services/conflicts.py`: інтервали `[start, end)`, стикання не є конфліктом, власна подія виключається, чужі події недоступні. Події «весь день» не беруть участі у перевірці конфліктів.
- Для кінцевих серій перевіряються всі екземпляри; для нескінченних — 365 днів від `max(start, now)`. Межа відображається у попередженні. Цей горизонт погоджено з користувачем.
- Конфлікти перевіряються при створенні, редагуванні та переміщенні. «Зберегти все одно» дозволяє лише накладання, але не обходить валідацію даних і часу.
- `PATCH /api/events/<id>/move/`: `start`, `end` — ISO зі зміщенням, `force` — boolean. Для серії обов'язкове `occurrence_start` із `extendedProps` початкового екземпляра. Відповіді: 200 / 409 із `conflicts` та межами перевірки / 400 / 404.
- `POST /api/events/check-conflicts/`: `start`, `end`, необов'язковий власний `exclude_id`; перевірка конкретного інтервалу до 366 днів.

```sh
uv run python app/manage.py check
uv run python app/manage.py test accounts planner
```

```sh
uv run python app/manage.py createsuperuser
```
